# Rapport de session — v0.47.1 (24/11/2026)

Correctifs issus de l'audit v0.45–v0.47 : ouverture des fichiers qui exécutent du code, lecture des textes du Coffre hors du serveur, décompression bornée des fichiers Office, PDF sans `eval`, test de synchro instable. Aucune migration.

## Guide pour Thomas

**Un script n'est jamais lancé par un double-clic.**

- Dans le Coffre, un double-clic sur un fichier de code (`.py`, `.js`, `.ps1`, `.sh`, `.bat`, `.c`, `.json`…) l'ouvre dans **VS Code** s'il est installé, sinon dans l'**aperçu** de ToolBox. L'application associée de Windows (qui, pour un `.py` ou un `.ps1`, pourrait l'exécuter) n'est jamais utilisée sans ta confirmation.
- Le clic droit dit ce qu'il fera : « Ouvrir dans VS Code » ou « Aperçu (code : jamais lancé) ».
- Plus de types de fichiers demandent une confirmation avant d'être ouverts : Python (`.py`, `.pyw`…), AutoHotkey (`.ahk`), aide Windows (`.chm`), raccourcis ClickOnce et de réglages, scripts Windows (`.ws`, `.vb`), etc.
- Les images de disque (`.iso`, `.img`, `.vhd`, `.vhdx`) ont leur propre question : les ouvrir **monte** un lecteur sur le PC.

**ToolBox reste fluide pendant la lecture des textes.**

- La lecture des textes du Coffre (pour la recherche) se fait maintenant à part, hors de ce qui répond à l'interface : un gros PDF ou un gros document Word ne fige plus ToolBox.
- Un fichier qui prend plus de 60 s est marqué « illisible : trop long » et sera relu au prochain démarrage.
- Un fichier Office qui gonflerait énormément une fois décompressé est marqué « illisible : trop gros » et rien n'en est lu.
- Ces fichiers comptent dans « fichiers illisibles » de la Santé du coffre.

## 1. Résumé

- Les 5 points sont faits ; aucune migration.
- Scripts : liste des extensions complétée (avec les images de disque), double-clic sur un fichier de code → VS Code ou l'aperçu ; vérifié en réel (sans VS Code : l'aperçu, aucun appel « ouvrir »).
- Lecture des textes dans un worker, avec une durée maximale, relancé s'il s'arrête. Mesure : un gros `.docx` bloquait le serveur 0,6 s ; maintenant l'API répond toujours (14 ms d'attente au plus).
- Décompression Office bornée. PDF : l'option demandée n'existe plus dans pdf.js 6, qui n'a plus aucun `eval` ; un test le garantit.
- Test de synchro instable : le moteur était juste, le test supposait un ordre d'horloge ; rendu déterministe, suite de synchro verte 20 fois sur 20.

## 2. Ce qui a été fait

### 1 — Fichiers qui exécutent du code (`c25e41a`)

- `packages/sdk/core.ts` :
  - `RUNNABLE_EXTENSIONS` passe de 30 à environ 110 extensions, rangées en programmes, scripts, raccourcis et images de disque ;
  - nouveaux `MOUNTING_EXTENSIONS`, `mountsDisk(nom)` et `runnableQuestion(nom)` (la question qui nomme le fichier, et dit « monte » pour une image de disque).
- `ctx.files.open` (`backend/core/files.ts`) et la route `open` du Coffre : refus sans `runnable: true`, avec « monte une image de disque » ou « lance un programme ».
- Coffre :
  - `openPlan` (`frontend/logic.ts`) décide de l'ouverture : fichier de code (extension que le lecteur de code reconnaît) → VS Code s'il est installé, sinon l'aperçu ; projet → VS Code, sinon le dossier ; autre fichier → son application (confirmation pour un exécutable) ;
  - utilisée par le double-clic, Entrée, le bouton de l'aperçu et le libellé du clic droit (`frame.tsx`, `Preview.tsx`) ;
  - la fenêtre de lecture utilise la même question (`ReaderPage.tsx`).

**Référence pour la liste.** La page de Microsoft « Blocked attachments in Outlook » n'est pas joignable depuis cet environnement (réseau). La liste reprend donc les extensions de niveau 1 de cette page telles que je les connais, et les types que Windows (SmartScreen, « ouvrir le fichier ») traite comme dangereux :

- scripts Python (`py pyc pyo pyw pyz pyzw`), Perl / Ruby / shells (`pl rb sh csh ksh`), AutoHotkey ;
- PowerShell (`ps1 ps1xml ps2 ps2xml psc1 psc2 psd1 psm1 psdm1 pssc`, `msh*`) ;
- Windows Script (`ws wsc wsf wsh vb vbe vbp vbs js jse sct hta htc`) ;
- programmes et installateurs (`exe com scr pif cpl msi msp mst msu msix appx application appref-ms xbap gadget msc cab diagcab jar jnlp`) ;
- compléments Office et bases Access (`xll ade adp mde mdb…`) ;
- raccourcis et réglages (`lnk url website scf settingcontent-ms library-ms search-ms searchconnector-ms reg inf ins chm hlp`…) ;
- certificats (`cer crt der`) ;
- images de disque (`iso img vhd vhdx`).

**À vérifier contre la page officielle** quand le réseau le permettra (§9).

### 2, 3, 4 — Lecture hors du serveur, décompression bornée, PDF (`ff8de6f`)

- **Worker** :
  - `extract.worker.ts` lit un fichier ou un projet ; `extract-pool.ts` lui envoie un fichier à la fois ;
  - 60 s au plus par fichier : au-delà, état `toolong` (« illisible : trop long »), le worker est arrêté et remplacé, et le fichier est relu une fois au démarrage suivant ;
  - un worker qui s'arrête en cours de route (plantage) : « illisible : le lecteur s'est arrêté », puis un nouveau worker ;
  - `text-index.ts` n'appelle plus l'extraction dans le fil du serveur.
- **Build** générique (`scripts/esbuild-config.mjs`) : tout `modules/*/backend/*.worker.ts` est compilé dans `build/main/workers/<module>/`, dépaqueté de l'asar (`electron-builder.yml`). En développement et dans les tests, le Coffre le compile à la volée (esbuild, outil de développement, jamais chargé par l'app installée). pdf.js est transmis au worker par le fil principal.
- **Décompression** (`unzipBounded`, `extract.ts`) :
  - décompression en flux, par morceaux de 64 Ko, en comptant les octets produits ;
  - plafonds : 100 Mo par partie, 100 Mo en tout, 10 000 parties ;
  - au-delà, `TooBig` → état `toobig`, « illisible : trop gros », rien d'autre n'est lu.
- **PDF** :
  - pdf.js 6.5 n'a plus l'option `isEvalSupported`, et ses quatre versions embarquées (aperçu et extraction, normal et « legacy ») ne contiennent ni `new Function(` ni `eval(` ;
  - l'option, posée sans effet à l'extraction en v0.47.0, est retirée ; l'aperçu ne pouvait pas la recevoir (TypeScript la refuse) ;
  - `pdf-no-eval.test.ts` vérifie ces quatre fichiers et que la page de ToolBox reste sans `unsafe-eval` : il échouera si une mise à jour de pdf.js réintroduit un `eval`.
- Docs : ADR 0056 (note v0.47.1), ARCHITECTURE (« Workers des modules »), README du Coffre, MODULES.md §5 (`ctx.files.open`), cahier des charges (règle 4), CLAUDE.md.

### 5 — Test de synchro instable (`7a35c54`)

- **Cause** :
  - l'horloge de synchro est la chaîne « temps.compteur.appareil » ; les deux appareils la comparent de la même façon, donc **un seul gagnant, le même partout**, départagé par le temps, puis le compteur, puis l'identifiant d'appareil : le moteur était correct ;
  - le test faisait deux écritures sur le PC puis une sur le téléphone, et supposait celle du téléphone « plus récente » ;
  - dans la même milliseconde, le compteur du PC (deux écritures) ou, à compteurs égaux, l'identifiant d'appareil (aléatoire) pouvait l'emporter : le test échouait parfois, sur les deux appareils à la fois.
- **Correction** : le test attend la milliseconde suivante avant l'écriture du téléphone (`nextMillisecond`). Un nouveau test fige l'horloge des deux appareils (même temps, même compteur) et vérifie que le gagnant est celui de la plus grande horloge, le même sur le PC et le téléphone (champ et conflit).

## 4. Décisions prises sans Thomas

1. **Liste large plutôt qu'étroite** : tout le niveau 1 d'Outlook, y compris des types rarement dangereux (`cer`, `crt`, `theme`, `mdb`…). Une confirmation de trop coûte un clic ; un script lancé par erreur, beaucoup plus. Se règle dans `RUNNABLE_EXTENSIONS`.
2. **« Fichier de code » = ce que le lecteur de code reconnaît** (`languageOfExt`), y compris des fichiers qui ne s'exécutent pas (`.json`, `.c`, `.css`) : ils vont aussi dans VS Code ou l'aperçu, pour une règle simple et prévisible.
3. **Sans VS Code, le bouton « Ouvrir » de l'aperçu d'un fichier de code est masqué** : l'aperçu est déjà l'ouverture. « Afficher dans l'explorateur » reste.
4. **Plafonds** : 60 s par fichier ; 100 Mo décompressés par partie et en tout ; 10 000 parties.
5. **« Trop long » relu une fois par démarrage** (pas en boucle pendant la même session).
6. **Build générique des workers** (`*.worker.ts` de n'importe quel module) plutôt qu'une entrée propre au Coffre : le socle ne connaît pas le Coffre.

## 5. Écarts par rapport à la demande

- **Point 4** (« `isEvalSupported: false` comme l'extraction ») : l'option n'existe plus dans pdf.js 6.5, ni dans l'aperçu ni dans l'extraction, où elle était donc sans effet. Remplacée par un test qui garantit ce qu'elle visait : pas d'`eval` dans pdf.js, et la page l'interdit.
- **Mesure du point 2** : un PDF de 300 pages ne bloquait déjà pas beaucoup le serveur, car la v0.47.0 rendait la main entre deux pages. La mesure ajoute donc un gros `.docx`, lu d'un seul tenant, où la différence est nette (§7).

## 6. Bugs trouvés

1. **Option PDF sans effet** depuis la v0.47.0 (`isEvalSupported`) : sans conséquence, puisque pdf.js n'a plus d'`eval` ; retirée, et un test la remplace.
2. **Blocage du serveur par un gros fichier Office** (0,6 s pour 150 000 paragraphes, davantage pour un plus gros) : corrigé par le worker.
3. **Décompression non bornée** : un `.docx` piégé de moins de 2 Mo pouvait réclamer des Go de mémoire. Corrigé.
4. Au passage, dans le test de synchro : écrire une valeur identique à l'existante ne crée pas d'horloge pour ce champ (comportement voulu) ; le nouveau test utilise donc deux notes différentes.

## 9. Risques et points à surveiller

- La liste des extensions vient de la référence connue, pas d'une lecture en ligne de la page de Microsoft le jour même : à recouper quand le réseau le permettra.
- Un worker consomme un peu de mémoire en plus pendant la lecture (une instance de pdf.js) ; il est arrêté à la fermeture de ToolBox.
- Le worker de l'app installée tourne depuis `app.asar.unpacked` : vérifié dans le build Linux non empaqueté et par la CI Windows (smoke test de l'exe, contrôle `pdf-text`).
- Un fichier « trop long » à chaque démarrage sera retenté à chaque démarrage (60 s de lecture en arrière-plan) ; s'il le faut, on pourra espacer.
