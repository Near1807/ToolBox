# Rapport de session — v0.40.1 (Synchro : horloge correcte des champs restés à leur valeur par défaut) — 16/11/2026

Session « Synchro : horloge correcte des champs restés à leur valeur par défaut ». Correctif du défaut proposé au § 6 du rapport v0.40.0, décidé par Thomas.

## Guide pour Thomas

**Ce qui pouvait se perdre avant.**

- Certains champs restent à leur valeur de départ tant que personne n'y touche : « Facultatif » d'un événement, le timer associé d'une tâche ou d'un événement, les colonnes de source d'un import. Le moteur de synchro ne savait pas quand ces champs avaient été écrits. Il leur donnait la date de la **dernière** modification de l'élément sur l'appareil.
- Exemple : tu coches « Facultatif » sur le téléphone, puis tu changes la note du même cours sur le PC, puis tu synchronises. Le PC croyait que son « non facultatif » était plus récent que ton « Facultatif ».
  - Le PC gardait la note mais **refusait « Facultatif »** ;
  - le téléphone gardait les deux ;
  - les deux appareils n'étaient plus d'accord, et rien n'était listé dans « Conflits ».

**Ce qui est garanti maintenant.**

- Un champ jamais modifié prend la date de **création** de l'élément. Un vrai changement fait sur l'autre appareil est forcément plus récent : il passe toujours.
- Dans l'exemple ci-dessus, les deux appareils ont « Facultatif » **et** la nouvelle note.
- Si le **même** champ est changé sur les deux appareils entre deux synchros, le plus récent gagne et l'autre valeur va dans « Conflits », comme pour les autres champs.
- Toute colonne ajoutée plus tard est couverte de la même façon, sans rien faire dans le module.
- Rien ne change pour les données d'avant la synchro.

**À savoir.** Le PC et le téléphone doivent être **tous les deux en 0.40.1** pour se synchroniser. Si un seul est mis à jour, l'autre affiche « Mets à jour… » et ses changements attendent, intacts.

## 1. Résumé

- Correctif dans le moteur de synchro (`backend/core/sync/engine.ts`), le même code sur le PC et sur le téléphone : un champ sans horloge propre prend l'horloge la plus ancienne de sa ligne (sa création). Une ligne sans aucune horloge garde exactement le comportement d'avant.
- **Le point 2 n'était pas vrai tel quel** : les versions comparées étaient seulement celles des migrations. Sans migration, un PC en 0.40.1 et un téléphone en 0.40.0 se seraient synchronisés. J'ai ajouté aux versions comparées un numéro des règles du moteur, sans migration : ils sont maintenant bloqués (§ 4).
- Aucune migration, aucune horloge réécrite. 10 nouveaux tests ; lint, typecheck PC et téléphone, 1 140 tests verts ; les 12 références (6 modules, PC et téléphone) sont identiques.
- Montée de version depuis une base 0.40.0 synchronisée : 68 tables sur le PC et 68 sur le téléphone, **aucune modifiée** à l'ouverture.

## 2. Ce qui a été fait

### Correctif du moteur (`6bc7d1b`)

- `backend/core/sync/engine.ts` :
  - **Nouvelle fonction `rowFallback`** : l'horloge prêtée à un champ sans horloge propre. Si la ligne a des horloges de champ, c'est la plus ancienne (`MIN(hlc)` de `<module>__field_clock`, la création de la ligne). Sinon, c'est `updated_at`, comme avant.
  - **Échange (journaux, `applyRow`)** : utilise `rowFallback` pour le côté local.
  - **Première synchro « Fusionner » (instantanés, `applySnapshot`)** : même règle des deux côtés. Côté local, `rowFallback`. Côté reçu, la plus ancienne horloge de la ligne envoyée, sinon son `updated_at`.
  - **`SYNC_RULES_KEY = 'sync-engine'`, `SYNC_RULES = 1`**, ajoutés par `versions()` aux versions comparées.
- **Même code sur le téléphone** : le Worker importe le même `engine.ts` (`packages/phone/host.ts`, `sync-client.ts`). Aucune divergence possible.
- **Tests `tests/sync/default-columns.test.ts`** (10, sur deux vraies bases : PC better-sqlite3, téléphone sqlite-wasm) :
  1. Le cas du rapport : « Facultatif » sur le téléphone, note sur le PC → les deux gardés, sur les deux, 0 conflit.
  2. L'inverse : « Facultatif » sur le PC, lieu sur le téléphone → les deux gardés.
  3. « Facultatif » changé des deux côtés → le plus récent gagne, l'autre est dans « Conflits » sur les deux appareils.
  4. `timer_pref` de la To-do : sur le téléphone, et le titre changé sur le PC.
  5. Colonnes d'import (`source_id`, `origin_key`, `origin`) écrites sur le PC sur un événement fait à la main, la note changée sur le téléphone.
  6. Ligne sans aucune horloge : la dernière modification décide, comme avant. Ce test passait **avant** le correctif et passe à l'identique après.
  7. à 9. **Test générique** : une colonne ajoutée « par migration » (`ALTER TABLE` dans le test), en trois types (`INTEGER NOT NULL DEFAULT 0`, `TEXT NOT NULL DEFAULT 'aucun'`, `TEXT` nul). Dans les deux sens par l'échange, puis par une première synchro « Fusionner ».
  8. Versions : un appareil 0.40.0 (sans `sync-engine`) et un 0.40.1 n'échangent rien. Le PC refuse dans les deux sens, le téléphone voit aussi la différence, la première synchro est refusée, et le changement en attente part une fois les versions égales.
- **Avant le correctif**, 8 des 9 premiers tests échouaient : tous sauf le test 6, qui fixe le comportement d'avant. J'ai aussi vérifié que la partie « Fusionner » du correctif est nécessaire : sans elle, 2 des tests génériques échouent.
- **Documentation** : note v0.40.1 dans l'ADR 0044, `docs/MODULES.md` § 6 bis (champ sans horloge, versions comparées), `CLAUDE.md`.

## 4. Décisions prises sans Thomas

1. **Version des règles du moteur** (`sync-engine`). Le point 2 demandait de vérifier que le PC bloque deux appareils de versions différentes. Ce n'était pas le cas pour cette version : le blocage ne compare que les migrations, et ce correctif n'en a pas.
   - J'ai ajouté une clé aux versions comparées. Ce n'est pas une migration et rien n'est écrit dans la base.
   - Une app plus ancienne ne l'envoie pas, elle compte donc 0. Le blocage existant fait le reste dans les deux sens, avec ses messages habituels (« Mets à jour l'application… » ou « Mets à jour ToolBox sur le PC… »).
   - Sans ce blocage, un mélange 0.40.0 / 0.40.1 n'aurait pas été pire que deux 0.40.0 (seul l'appareil corrigé accepte davantage). Mais il ne correspondait pas à ce que tu attendais.
   - Pour revenir en arrière : retirer la clé dans `versions()`.
2. **« La plus ancienne horloge de la ligne »** plutôt que la date `created_at` de la ligne. C'est l'horloge du changement de création, identique sur les deux appareils, alors que `created_at` est une heure locale.
3. **Même règle pour la première synchro « Fusionner »**, pas seulement pour l'échange habituel : sinon le défaut restait possible à la première synchro.
4. **Une ligne qui a quelques horloges, mais dont des champs ont été écrits avant la synchro** (cas rare : une donnée d'avant la synchro modifiée ensuite). Ces champs prennent aussi la plus ancienne horloge de la ligne. Leur vraie valeur est plus ancienne qu'elle, donc la règle reste juste.

## 9. Risques et points à surveiller

- **Mise à jour des deux appareils obligatoire** : tant que le téléphone est en 0.40.0, la synchro est arrêtée (voulu).
- **Données déjà divergentes** : si le défaut a déjà touché un élément avant cette version, il reste différent sur les deux appareils. La synchro ne corrige pas une différence passée sans nouveau changement. Il suffit de rechanger le champ sur l'appareil qui a la bonne valeur.
- **Future règle de fusion sans migration** : il faudra relever `SYNC_RULES` (noté dans `CLAUDE.md`, l'ADR 0044 et le code).
- **Écriture hors `SyncStore`** (interdite par le contrat, par exemple une migration qui remplit une colonne après la synchro) : la valeur écrite prendrait l'horloge de création. Le cas ne se présente que si les deux appareils ne passent pas la même migration, ce que la comparaison des versions empêche.
