Dans ce journal, le mot « toolbox » est remplacé par `***` (par exemple `be.***.app`). GitHub masque toute valeur égale à un secret, et l'alias de la clé vaut « toolbox ». C'est normal.

3. **Cocher une tâche** (la case à gauche de « Ranger le bureau »).
   - Attendu : elle passe dans l'onglet « Faites » (compteur 1) ; « 2 à faire ».
4. **Supprimer une tâche, puis annuler.**

   - Attendu : tout est là (2 à faire, 1 faite, tags et échéances).
6. **Mode avion** activé, puis ouvrir l'appli, ajouter une tâche, en cocher une.
   - Attendu : tout marche normalement, car rien ne passe par Internet. Tu peux couper le mode avion ensuite.

   « Restaurer une copie » affiche la liste. **Ne restaure rien pour l'essai** : touche « Annuler ».

### 5. Installer une future mise à jour par-dessus

1. Chaque nouvelle version de ToolBox (0.30.1, 0.31.0…) donne un nouvel APK, avec un versionCode plus grand, dans le run « Android (ToolBox) » correspondant.
2. Télécharge-le comme à l'étape 1 et touche-le.
   - Android affiche « Voulez-vous mettre à jour cette application ? » › **Mettre à jour**.
   - **Tes tâches restent** : même identifiant, même clé.
3. **Ne désinstalle jamais l'appli pour la mettre à jour** : désinstaller efface ses données et ses copies de sauvegarde.
4. Si Android refuse (« Application non installée ») : l'APK n'est pas signé avec ta clé, ou sa version n'est pas plus récente. Ne force rien et envoie-moi le message.

## 1. Résumé

- **ToolBox sur Android** (`mobile/app/`, `be.toolbox.app`) :
  - Accueil, To-do et Réglages, navigation en bas ;
  - les écrans To-do du PC avec une mise en page mobile ;
  - les thèmes ; un démarrage à vide.
- **Hôte téléphone** (`packages/phone/`) : le code serveur de la To-do tourne **tel quel** dans un Worker, avec une base SQLite WebAssembly sur OPFS.
  - **Preuve clé** : la référence de non-régression de la To-do, rejouée sur sqlite-wasm et l'hôte téléphone, donne **exactement** les mêmes réponses et les mêmes lignes stockées qu'avec better-sqlite3 et Fastify.
- **Filet de sauvegarde** : une copie par jour, 7 gardées, restauration proposée et jamais automatique.
- **APK release signé** construit et vérifié par la CI (vert).
- **PC** : aucun changement de comportement (références des 5 modules vertes).
- **Sur le S21** : **non testé en réel** ; c'est l'objet du guide ci-dessus.

### Partie B — hôte téléphone (`f348678`, `f2123f5`)

- **`packages/phone/host.ts`** :
  - `PhoneHub` construit le même `ctx` que le socle : `db`, `routes`, `settings` (table `core__settings` du PC), `services`, `calendar`, `logger`, `onShutdown` ;
  - il réutilise **tels quels** les registres de services et de calendrier du socle et son ordre de chargement ;
  - il fait tourner les migrations du socle (`core`) puis celles des modules, avec le même exécuteur que le PC ;
  - `files`, `images`, `notifications`, `outputs`, `jobs`, `scheduler`, `events`, `ui`, `hotkeys`, `accounts`, `binaries` et `db.backup` lèvent « « ctx.files.readFile » n'est pas disponible sur le téléphone. » ;
  - `assistant` est sans effet (`define` accepté et ignoré) ;
  - `register(ctx)` de la To-do est appelé tel quel.
- **`packages/phone/router.ts`** (mini routeur) : méthode + chemin + `:params`, query (tableaux pour les clés répétées), corps JSON. Il reproduit les réponses de Fastify :
  - HttpError → `{ error }` ;
  - AccountError → 409 ;
  - erreur → 500 « Erreur dans « To-do » : … » ;
  - route inconnue → 404 de Fastify ;
  - JSON invalide ou vide → 400 ;
  - corps trop gros → 413 ;
  - route du socle `GET /api/core/calendar`.
- **`packages/phone/transport.ts`** : `WorkerClient` (messages page ↔ Worker) et `workerTransport`, donné à `setApiTransport` au démarrage. Les écrans ne changent pas. Les flux d'événements disent clairement qu'ils ne sont pas disponibles.
- **`mobile/app/src/worker.ts`** : ouvre SQLite sur OPFS (pool `toolbox`, fichier `/toolbox.sqlite3`) et sert les requêtes, l'état de la base, la copie et la restauration. Si OPFS manque, l'appli affiche « ToolBox ne peut pas démarrer » avec la raison, sans aucun repli.

### Partie C — base sqlite-wasm (`f348678`)

- **`packages/phone/database.ts`** : l'interface de better-sqlite3 utilisée par le socle et les modules :
  - `prepare` → `run` / `get` / `all` ;
  - `exec`, `transaction` (imbriquées en savepoints).
- **Comportement de better-sqlite3 reproduit** :
  - objets de ligne simples ;
  - entiers en nombres ;
  - `undefined` lié comme NULL ;
  - booléens refusés ;
  - nombre de paramètres vérifié ;
  - `changes` à 0 pour un SELECT ;
  - messages d'erreur sans le préfixe de sqlite-wasm, `code` `SQLITE_…`.
- **Exécuteur de migrations rendu portable sans changement pour le PC** :
  - `backend/core/migrations-core.ts` reçoit ses fonctions de plateforme ;
  - `backend/core/migrations.ts` lui passe celles de Node.
- **Autres parties portables** :
  - validation des réglages (`settings-validation.ts`) ;
  - format des identifiants hérités (`legacy-id-core.ts`).
- **`packages/phone/sha256.ts`** : sha256 synchrone en JavaScript. Une installation neuve convertit les 2 préréglages livrés du Timer avec `legacyId`, ce qui exige un sha256 synchrone. Il est égal à celui de Node.

### Partie D — filet de sauvegarde (`f2123f5`)

- **Règles pures** (`packages/phone/backup.ts`, testées) :
  - copie du jour seulement si aucune n'existe aujourd'hui et si la base n'est **pas vide** ;
  - 7 copies gardées ;
  - offre de restauration seulement si la base est absente ou vide **et** qu'une copie avec des données existe.
- **Côté appli** (`mobile/app/src/backup.ts`) :
  - stockage : plugin Filesystem, `Directory.Data/copies/` ; chaque copie = base (`.sqlite3`) + fiche (`.json` : date, nombre de tâches, version) ;
  - la fiche est écrite en dernier, donc une copie à moitié écrite n'est jamais listée ;
  - **à l'ouverture** : si l'offre s'applique, l'écran « Données introuvables » donne la date et le nombre de tâches, avec « Restaurer cette copie » (puis une confirmation) ou « Continuer sans restaurer ». Jamais de restauration automatique. Sinon, la copie du jour.
- **Réglages** :
  - date de la dernière copie ;
  - « Restaurer une copie » : liste (date, tâches, version), confirmation ;
  - si la base contient des données, une copie « avant-restauration » est faite d'abord.

## 4. Décisions prises sans Thomas

1. **Mot de passe de la clé** : le workflow utilise celui du magasin pour la clé (PKCS12 : un seul mot de passe), et avertit si `ANDROID_KEY_PASSWORD` diffère. C'était le cas au premier run, qui a échoué ; le second est vert. Pour revenir à `ANDROID_KEY_PASSWORD` : corrige le secret, puis demande-moi de remettre la ligne.
2. **`android:allowBackup="false"`** : sinon Android envoie les données de l'appli vers Google Drive tout seul, ce qui serait « envoyer en ligne » sans ton accord. Conséquence : à une réinstallation, rien n'est restauré par Google. Le filet local reste.
3. **Jamais de copie d'une base vide** : une base vidée par Android ne doit pas chasser les bonnes copies, une par jour.
4. **Offre de restauration** : la copie la plus récente **qui contient des données** ; une copie vide n'est jamais proposée.
5. **Copie « avant-restauration »** : faite automatiquement avant de remplacer une base non vide depuis Réglages. Elle compte dans les 7 copies gardées. La copie à restaurer est lue d'abord, pour que la rotation ne puisse pas la supprimer.
6. **Le téléphone fait tourner les migrations du socle** (`core__*`) comme le PC : même schéma, utile pour la future empreinte de version de la synchro. Il n'y a pas de sauvegarde avant migration sur le téléphone (le filet quotidien en tient lieu).
7. **Réglages de module** : même table `core__settings` que le PC. Les secrets et les réglages de dossier ne sont pas disponibles sur le téléphone (erreur explicite).
8. **sha256 en JavaScript** pour `legacyId`, prouvé égal à celui de Node sur 400 textes. Sans lui, le Timer ne démarrerait pas sur le téléphone.
9. **React, Vite et sqlite-wasm pris à la racine** (une seule version épinglée, celle du PC). `@sqlite.org/sqlite-wasm` 3.54.1-build1 (la version de l'essai) est ajouté aux devDependencies de la racine, pour les tests et l'appli.
10. **CSP de l'appli** : `script-src 'self' 'wasm-unsafe-eval'` (WebAssembly), `worker-src 'self' blob:`.

## 9. Risques et points à surveiller

- **WebView du S21** : CSP, Worker module, plugin Filesystem et dialogues de confirmation ne sont vérifiés que dans Chromium de bureau, **non testés en réel**.
- **`storage.persist()` = non** : Android peut effacer OPFS si le téléphone manque de place. Le filet le couvre jusqu'à 7 jours en arrière. Les copies vivent dans le stockage de l'appli et disparaissent avec une **désinstallation**.
- **Migrations sur le téléphone** : pas de sauvegarde automatique juste avant (seulement la copie quotidienne). À ajouter avant la première migration qui touche des données existantes du téléphone.
- **Pas de verrou** entre une copie et une écriture : elles se suivent dans le même Worker, sans transaction ouverte entre deux appels.
- **Dépendances** : l'appli dépend de la racine (`npm ci` à la racine pour la construire). Une mise à jour de React ou Vite à la racine change aussi l'appli.
- **`setup-android@v3`** tourne sur Node 20, déprécié (avertissement).
